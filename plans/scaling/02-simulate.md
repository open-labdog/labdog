# Step 2 — Load-test harness (simulated 200–300 hosts)

Purpose: see how LabDog behaves at 200–300 hosts with a busy, mixed
schedule, on a **separate** LabDog instance. Never point this at the live
install or its hosts.

Deliverables (all committed to this branch):

- `dev/loadtest/` — compose file, fake-host image, seed script, scenario
  runner, metrics sampler, README.
- `plans/scaling/results/02-baseline.md` — numbers on unchanged code.

Step 3 reruns the same scenarios; keep the harness stable once the
baseline is recorded.

## Fake hosts

- Image: Debian slim + `openssh-server` + `python3` + `sudo` + `cron`,
  passwordless sudo for a `labdog` user, an authorised key baked in at
  build time from a key generated by the seed script.
- `docker compose up --scale fakehost=N` on a private bridge network.
  Size each container small (`mem_limit: 64m`); 300 of them should fit
  in ~10–15 GB on the test machine. Document the host requirement.
- Optional latency: `tc qdisc add dev eth0 root netem delay 20ms` in the
  entrypoint behind an env var, to mimic hosts not on the same box.
  Needs `cap_add: NET_ADMIN`.

### What works in a container and what doesn't

| Module | In a plain container | Notes |
| --- | --- | --- |
| hosts_file, resolver, linux_user, cron, package | Works | Use these for sync + drift load |
| firewall | Needs `NET_ADMIN` + nftables installed | Enable on a subset only, or skip |
| service | Needs systemd as PID 1 | Skip; note it in results |
| Actions | Use a harmless action | See below |

Harmless action: add `dev/loadtest/pack/actions/loadtest-sleep/` (a
local pack) with a playbook that gathers facts, sleeps for a
`duration` parameter (default 30 s) and writes a file under `/tmp`.
Register it as a local-directory pack in the test instance. Its key must
not collide with `labdog-playbooks` keys.

## Seeding

`dev/loadtest/seed.py`, using the public REST API only (no DB writes),
so it exercises the same paths an operator would:

1. Register the admin user (fresh instance) and log in.
2. `POST /api/ssh-keys` with the generated key.
3. `POST /api/hosts` for each fake host (IP from `docker inspect`).
4. Create 3–5 groups (by index ranges) with config in the container-safe
   modules, so syncs have real work. Overlapping membership on purpose,
   to exercise the per-host lock.
5. Enable drift for the container-safe modules on every host.
6. Register the local pack and run `POST /api/actions/refresh`.

## Scenarios

Each scenario runs for a fixed window (default 60 min) after a 10 min
warm-up, so drift sweeps tick at least twice
(`drift.check_interval_minutes` can be set to 15 on the test instance
to shorten this; record the value used).

| ID | Load | What it shows |
| --- | --- | --- |
| S1 | Drift only, N = 50 / 150 / 300 | Does a sweep finish within its interval? Slot occupancy from drift alone |
| S2 | S1 + bulk sync of all hosts every 15 min | Sync wait time while drift runs |
| S3 | S2 + 8 scheduled actions on staggered minutes, different groups, parallelism 10 | Orchestrator cap, queue wait |
| S4 | S3 + one action with parallelism 0 (all hosts) at minute 20 | Fairness: does one big run starve the rest? |
| S5 | S3 with 4 actions on the same cron minute targeting overlapping groups | Per-host lock contention |

Run each scenario at two configs on unchanged code:

- Defaults: `celery.concurrency = 4`, `orchestrator_concurrency = 4`.
- Raised: `celery.concurrency = 16`, `orchestrator_concurrency = 12`.

The raised config is "scale up without splitting" and is the baseline
step 3 must beat.

## Metrics

`dev/loadtest/sample.sh` writes a CSV every 10 s:

- Container RSS (`docker stats --no-stream`).
- Queue depth per queue (`redis-cli LLEN default`, `long_running`,
  `orchestrator`).
- Postgres connections (`pg_stat_activity`).
- Rows in `running` and `pending` for `sync_jobs`, `action_runs`,
  `action_host_runs`.

After the run, reuse the step 1 queries (`dev/loadtest/measure_live.sql`)
against the test database for drift time, sync/action duration and
queue wait.

Results per scenario × config: hosts completed per hour, p50/p95 queue
wait, p95 drift sweep duration vs interval, peak RSS, peak connections,
any failures or stuck rows.

## Out of scope

- Real network partitions or flaky hosts beyond `netem` delay. A
  follow-up could stop 10% of fake hosts mid-run to measure the
  connect-timeout cost on serial sweeps.
- Multi-site runner routing (only matters once step 3 lands).
